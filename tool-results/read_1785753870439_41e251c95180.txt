     8→     8→## 1. Executive Summary
     9→     9→
    10→    10→The application is functional in production and represents a significant amount of well-structured work. Core payroll calculation, ESS login, attendance, and document flows operate correctly. Security fundamentals are solid — prepared statements throughout, bcrypt passwords, CSRF on most forms, parameterised queries everywhere inspected.
    11→    11→
    12→    12→However, **4 critical issues** must be addressed before the system can be considered production-safe at scale:
    13→    13→1. CORS blocks the `X-API-KEY` header — all ESS API calls will fail in strict browsers
    14→    14→2. `payroll` table INSERT does not write `month`/`year` — all reports return zero rows for new payroll runs
    15→    15→3. WhatsApp server has a hardcoded API key committed to the public repo
    16→    16→4. Bonus and gratuity provisions use pro-rated basic_da — legally incorrect under the Payment of Bonus Act
    17→    17→

    22→    22→## 2. Critical Issues
    23→    23→
    24→    24→### C1 — CORS missing `X-API-KEY` in `Access-Control-Allow-Headers`
    25→    25→- **Severity:** Critical
    26→    26→- **File:** `api/ess/cors.php`
    27→    27→- **Current:** `Access-Control-Allow-Headers: Content-Type, Authorization, X-Requested-With, Cache-Control`
    28→    28→- **Expected:** Must include `X-API-KEY`
    29→    29→- **Risk:** Every cross-origin ESS API call sends `X-API-KEY` as a custom header. When browsers send a CORS preflight (OPTIONS), the server must declare this header allowed. Without it, Chrome/Firefox block the actual request. Works in development (same-origin) but breaks in production cross-origin scenarios.
    30→    30→- **Fix:**
    31→    31→```php
    32→    32→// cors.php — both header() calls
    33→    33→header('Access-Control-Allow-Headers: Content-Type, Authorization, X-Requested-With, Cache-Control, X-API-KEY');
    34→    34→```
    35→    35→- **DB Migration Required:** No
    36→    36→

    39→    39→### C2 — `payroll` INSERT missing `month` and `year` columns
    40→    40→- **Severity:** Critical
    41→    41→- **File:** `php_payroll/includes/class.payroll.php` line 636
    42→    42→- **Table:** `payroll`
    43→    43→- **Current:** INSERT into `payroll` does not include `month` or `year` in column list or VALUES
    44→    44→- **Expected:** All reports (`view.php:191`, `bank-advice.php:23`, `salary-register.php:23`) filter with `WHERE p.month = :month AND p.year = :year`
    45→    45→- **Risk:** Every new payroll run creates rows with NULL month/year. Every report returns zero rows. The bank advice page uses `SELECT DISTINCT month, year FROM payroll` to populate the dropdown — it will be empty for new runs.
    46→    46→- **Fix — `class.payroll.php` line 636:**
    47→    47→```php
    48→    48→// ADD to INSERT column list:
    49→    49→payroll_period_id, employee_id, unit_id, month, year,
    50→    50→// ADD to VALUES:
    51→    51→:period_id, :emp_code, :unit_id, :month, :year,
    52→    52→// ADD to ON DUPLICATE KEY UPDATE:
    53→    53→month = VALUES(month), year = VALUES(year),
    54→    54→// ADD to params array:
    55→    55→'month' => $period['month'],
    56→    56→'year'  => $period['year'],
    57→    57→```
    58→    58→- **DB Migration Required:** Verify `payroll` table has `month INT` and `year INT` columns. If not:
    59→    59→```sql
    60→    60→ALTER TABLE payroll
    61→    61→  ADD COLUMN month TINYINT(2) NOT NULL DEFAULT 0 AFTER unit_id,
    62→    62→  ADD COLUMN year  SMALLINT(4) NOT NULL DEFAULT 0 AFTER month,
    63→    63→  ADD INDEX idx_month_year (month, year);
    64→    64→```

    85→    85→### C4 — Bonus and gratuity provisions use pro-rated `basicDa` (legally incorrect)
    86→    86→- **Severity:** Critical (financial compliance)
    87→    87→- **File:** `php_payroll/includes/class.payroll.php` lines 602–609
    88→    88→- **Current:**
    89→    89→```php
    90→    90→$bonusBase = min($basicDa, 7000);  // $basicDa is pro-rated by paid_days
    91→    91→$bonusProvision = round($bonusBase * 8.33 / 100, 2);
    92→    92→$gratuityProvision = round($basicDa * 4.81 / 100, 2);
    93→    93→```
    94→    94→- **Expected:** Payment of Bonus Act requires 8.33% of **monthly wages** (full month), not days-attended. An employee present 15/30 days gets half the statutory bonus provision — under-provisioned.
    95→    95→- **Risk:** Understated bonus liability in P&L, potential Bonus Act non-compliance during audit.
    96→    96→- **Fix:**
    97→    97→```php
    98→    98→$fullMonthBasicDa  = floatval($emp['basic_da'] ?? 0);
    99→    99→$bonusBase         = min($fullMonthBasicDa, 7000);
   100→   100→$bonusProvision    = $emp['bonus_applicable'] ? round($bonusBase * 8.33 / 100, 2) : 0;
   101→   101→$gratuityProvision = $emp['gratuity_applicable'] ? round($fullMonthBasicDa * 4.81 / 100, 2) : 0;
   102→   102→```
   103→   103→- **DB Migration Required:** No (code fix only; past payroll will need recalculation if required)

   127→   127→### H3 — Two separate DB queries for same `employee_advances` row per employee
   128→   128→- **Severity:** High (performance)
   129→   129→- **File:** `php_payroll/includes/class.payroll.php` lines 555–570
   130→   130→- **Current:** Two identical `WHERE employee_id + unit_id + month + year` queries — one for `adv1+adv2+dress_advance`, one for `office_advance`
   131→   131→- **Risk:** For 500 employees, this is 1,000 advance queries per payroll run instead of 500. Under concurrent payroll runs this causes DB lock contention.
   132→   132→- **Fix:** Merge into one query:
   133→   133→```php
   134→   134→$advRow = $this->db->fetch(
   135→   135→    "SELECT COALESCE(SUM(adv1+adv2+dress_advance),0) as total_advance,
   136→   136→            COALESCE(SUM(office_advance),0) as office_ded
   137→   137→     FROM employee_advances
   138→   138→     WHERE employee_id=:e AND unit_id=:u AND month=:m AND year=:y",
   139→   139→    ['e'=>$emp['id'],'u'=>$emp['unit_id'],'m'=>$period['month'],'y'=>$period['year']]
   140→   140→);
   141→   141→```
